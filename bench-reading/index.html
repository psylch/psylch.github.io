Bench 精读Lectio Benchmarkorum精读之印

先看结论

  1. 只查终态，不查过程。判分对象是任务结束后留下的状态和文件，不是点击序列或终端输出。所以 GUI、MCP、代码三种接口可以共用一套 verifier。Terminal-Bench OSWorld 2.0 CUA-Gym Kimi K3
  2. 能用程序判的不用模型判。必须用模型时，只让它判二值条目，并且先和人工对过一致率。CraftBench-UE OSWorld 2.0 BlenderWorld GDPval
  3. verifier 有两种错，都要审。没做对却给分（假阳性），做对了却不给分（假阴性）。前者让分数虚高，后者在 RL 里等于惩罚正确行为。Terminal-Bench SWE-bench Pro OSWorld 2.0 VeriCUA 奖励版
  4. 一道题的准入线：参考解必须通过，什么都不做必须失败，再放一个专门作弊的 agent 去试。Terminal-Bench 作弊 agent CraftBench-UE CUA-Gym
  5. 造答案的和写判分的要隔开。同一方既造标准答案又写判分，判分就会去核对「我是怎么造的」而不是「任务做成没有」。CUA-Gym Kimi K3 Terminal-Bench
  6. 测评用的 verifier 和训练用的 reward 不是一回事。测评要精确、可人工逐题审；训练要量大、信号密、经得住策略钻空子。OSWorld 2.0 Echoverse VeriCUA 奖励版
  7. bench 和环境是要持续修的东西。模型跑出来的失败里，有相当一部分是环境、任务或判分的错。Echoverse VeriCUA Terminal-Bench

bench 怎么造

  • 任务单元。通用版是四件套：环境、指令、测试、人写的参考解 TB。UE 版多两样：可写范围和引擎版本 CraftBench。训练环境版是指令、初始状态、reward 函数一起生成 CUA-Gym。
  • 题从哪来。众包后筛掉六成 TB；真实 commit 加人工补全描述 SWE Pro；内部标注员一手包办 OSWorld 2.0；行业专家的真实工作成果 GDPval；人定画像和偏好、模型合成历史 VitaBench。
  • 规模都不大。89、108、70、223 题。质量靠审：每题约 3 小时 TB，每题平均 5 次人审 GDPval，三层质检 OSWorld 2.0。
  • 把想测的能力隔离出来。埋两类干扰项，只有用上偏好才能选对 VitaBench；同一玩法出 C++ 和 Blueprint 两个版本 CraftBench；去掉人工补全做消融 SWE Pro。
  • 防污染。选 copyleft 仓库、买私有代码、留一个从不公开成绩的留出集 SWE Pro 三集划分。只放 canary 字符串基本没用 TB。
  • 难度要实测。人估的难度和模型实测难度只有中等相关 TB。

verifier 怎么设计

  • 第一档：确定性终态检查。容器里跑测试 TB，比较应用状态的差异 CUA-Gym，把数据库当状态 Echoverse，引擎里跑断言 CraftBench。
  • 第二档：拆成 checkpoint 给部分分。平均每题 27.25 个，同时报全过率和部分分 OSWorld 2.0。
  • 第三档：二值判据加 judge。判据带原文出处，按证据类型分给看图的 judge 和能打开工程的 judge BlenderWorld Agent judge。
  • 第四档：verifier 自己去取证。agent 说「做完了」不算证据，要有实际读到的文件或状态 VeriCUA 判定规则；检查值不值得做要执行了才知道 奖励版。
  • 第五档：专家盲评。最贵，用在没有标准答案的交付物上 GDPval。
  • 行为要在运行时查。过了资产检查的 Blueprint，四成到一半在运行时断言上失败 CraftBench 对照。
  • agent 的自检不能当验收。它会改写自己的检查目标 BlenderWorld，也更爱查资产而不是运行状态 CraftBench。
  • judge 要报一致率。90% TB；两个作品接近时掉到 68.57% BlenderWorld；偏爱自家模型 GDPval。
  • 终态评分看不出绕路。约 14% 的轨迹去读隐藏状态，约 33% 绕过界面 OSWorld 2.0。

好数据长什么样

  • 带着能跑的判分。一条训练数据合格的操作定义：目标状态判 1.0，初始状态判 0.0，判分代码里没有偷懒写法 CUA-Gym。
  • 思考是当场录的。先录操作、事后补推理这条路行不通，所以让标注员边做边说 UI-TARS-2。
  • 贴着当前模型会走到的状态。模型提候选动作，人接受或改写 UI-TARS-2。
  • 按质量分流，不是一刀切丢弃。通过校验的进 SFT，没通过的回到前面的预训练阶段 UI-TARS-2。
  • 真值由人定，体量由模型补。VitaBench 防泄露审查
  • 过滤要有账。投票拒约 3,100 条，实跑再拒 1,278 条，留下 32,112 条 CUA-Gym。
  • 环境要「深」。工作流能端到端走通并留下可查的痕迹 Echoverse。在浅环境上训练，真实网站成绩反而下降 结果。
  • 环境多样性的证据还弱。论文自己的对照里，翻倍轨迹量的提升更大 CUA-Gym。
  • 推断人类专家轨迹的位置在冷启动：SFT 数据、参考解、人类耗时基线。RL 阶段缺的不是更多轨迹，而是环境和 verifier。

RL 后训练入门

  • 几个词。被训练的模型叫 policy；它完整做一遍任务叫 rollout；做完得到的分数叫 reward；模型钻判分漏洞拿高分叫 reward hacking。
  • 三段流程。SFT 用示范数据给一个能用的起点，RL 在环境里反复试并按 reward 更新，最后把多个专家模型合并成一个 Kimi K3 UI-TARS-2。
  • reward 的三个来源。确定性规则或 verifier K3 UI-TARS-2；让模型当评委按 rubric 比较 K3；让模型看轨迹判成败 UI-TARS-2。
  • 长任务的 reward 太稀。五十步只得到一比特信号 Echoverse。办法有：加逐步打分但终态说了算 Echoverse；预训练一个估值模型 UI-TARS-2；蒸馏时逐 token 给信号 K3。
  • reward 可以直接表达行为要求。超出 token 预算就给 −1 K3；探查后判对比直接判对少给一点，教会 verifier 什么时候才该探查 奖励表。
  • 防 reward hacking 靠结构。agent 和 verifier 隔离，另设隐藏 verifier，限制提交次数 K3；沙箱要防的是模型本身 K3。训练曲线平稳只是旁证 CUA-Gym。
  • 别过拟合某一家工具。训练时随机组合工具接口和提示 K3。
  • verifier 本身也可以训。提示出来的 judge 卡在 68% 到 70% 奖励版，训练后能当更好的 reward 下游效果。
  • 说明头部闭源实验室不公开自己的配方。这一节来自 Kimi K3、UI-TARS-2 等公开报告，它们没给任务数量、奖励权重、作弊发生率这类关键数字。

给 CUA + UE bench 的设计建议 推断

  1. 任务包六样：起始工程、指令、可写范围、引擎版本、verifier、参考解。参考解可以直接取专家轨迹结束时的工程。依据
  2. 评落盘的工程：把允许改动的文件拷进全新工程副本，重建后再判。编辑器里没保存的状态不算。依据
  3. 三层确定性检查：能否构建；无界面加载资产查结构；固定步长运行后查行为断言。资产 确定性
  4. 视觉质量另走一条线：二值判据带出处，judge 能打开工程而不只是看渲染图，并报它和人的一致率。依据 一致性
  5. 长任务拆 checkpoint：同时报全过率和部分分，避免「做对大半」和「完全没做」得一样的分。依据
  6. 准入四步：参考解通过；起始工程失败；作弊 agent 跑一遍；多个强模型试跑后做失败归因。归因
  7. 接口不限，但当变量记录：文件加 shell、不同 MCP、GUI 的成绩差别很大，也要另外审计绕路行为。依据 混合环境
  8. 从第一天留私有集。依据
  9. 还没有现成答案的三件事：需要交互拨动控件才能判的质量 BlenderWorld；UE 这类重型应用的并行评测成本；渲染和物理的非确定性之外的手感类判断。
