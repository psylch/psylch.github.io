剪辑软件轨迹字段设计 v1（PR / 剪映 / 达芬奇）

结论

  • 格式不重做：沿用 v0.2（原始事件层 + 语义步视图、L0–L4、provenance、op_native→op_canonical、Contra 列兼容）。新增 editing.* 领域扩展：时间线状态快照、时间线差分、剪辑动作词表、「看」行为（播放/擦洗）记录。
  • 三款软件 L2 能力差距大：PR（UXP 25.6+）= 有事件 + 可读写时间线，L2 最强；达芬奇 = 只有 Studio 能脚本，且无事件回调，只能轮询；剪映 = 无插件 API，6.0 起草稿加密，新版 UI 不暴露 AX，只能靠 L3 + 草稿差分。
  • 剪辑的核心事实是「时间线状态序列」：动作可以缺，但每个关键时刻的时间线快照必须有。统一语义步优先从「快照差分」派生（diff 推断 op，标 provenance=derived），PR 原生事件只作为加分。
  • 预览/擦洗是剪辑独有的高价值信号（找剪点、比对、回看），按「播放段」合并记录，不逐帧落盘。
  • 任务包 = 工程文件（逐次保存版本）+ 导出成片 + 素材清单（哈希，不含素材本体，按需求方授权附代理） + 轨迹 + 剪辑理由。第一阶段 P0 推荐 PR 为主采软件，达芬奇 Studio 为次，剪映走「低保真」档并单独标注。

三款软件采集面

能力等级（L2）

软件 L2 等级 能拿到 缺口

Premiere Pro

  • UXP：require('premierepro')，方法异步不阻塞 UI；EventManager since 25.6。
  • ExtendScript/CEP：仍受支持；CEP 预计 2028-12 在 PR 默认禁用、2029 年底移除 → 新插件直接用 UXP，旧版本 PR（<25.6）才用 CEP 兜底。
  • 工程：.prproj（gzip XML，可离线解析，作为 L2 缺失时的保存点差分来源）；可导出 FCP XML。
  • 采集方式：UXP 面板常驻 → 订阅事件 → 事件触发 + 定时（如 2s）读活动序列快照 → 差分。

DaVinci Resolve

  • 脚本入口 DaVinciResolveScript，外部脚本需 Studio 且偏好设为 Local。
  • 轮询：建议 1–2s 读「当前页面、当前时间线、当前时间码、选中项（待验证 API 覆盖）」，5–10s 或在 L3 检测到编辑键/鼠标释放后读全量轨道快照。
  • 工程在数据库内（.drp 可导出）；时间线可导出 EDL/FCPXML/AAF/OTIO（OTIO 版本支持待验证）。
  • 采集对象选 Studio（合作方在岗剪辑师多有 Studio，待确认）。

剪映专业版 / CapCut 桌面

  • 只做：L0 环境 + L3（截帧 + 键鼠，坐标）+ 草稿差分（仅明文版本：剪映 ≤5.9.x 或 CapCut 国际版）+ 导出物。
  • 加密版本：不解密；只记草稿文件的大小/mtime/哈希变化作为「保存点」信号，语义全部来自 L3 + 模型标注（provenance=model）。
  • 结论：剪映数据定为「低保真档」，单独定价/标注，不与 PR/达芬奇混为同一质量等级。

扩展到建模

公共核心 + 领域扩展

  • 公共核心（不变）：事件公共字段、action{op_native, op_canonical, params, phase, trigger, context}、changes[]、history、intent、provenance、Contra 列。
  • 领域扩展挂在命名空间下：事件 payload 原样保留；结构化扩展放 ext.editing.* / ext.modeling.*；manifest 声明 domains: ["editing"] 与 ext_versions: {"editing": "0.1"}。
  • 词表：公共动词保持原 id（file.*、history.*、select.set、property.set、view.navigate、script.run、anim.insert_keyframe）；领域专有动作用二级前缀（editing.clip.cut、modeling.geometry.extrude）。现有 P0 的 geometry.*/sketch.*/paint.* 迁移为 modeling.* 别名（保留旧 id 一个版本）。
  • 建模域示例：ext.modeling.scene_snapshot（对象树、变换、修改器栈）沿用 Blender/UE/FreeCAD 已有 L2 快照；ext.editing.timeline_snapshot 与之并列，changes[].target.type 各域自定义但须带域前缀时可无歧义（如 editing:item、modeling:object）。
  • 跨域公共语义：时间轴（anim.set_frame ↔ 播放头）、关键帧、节点图（调色节点 ↔ 材质节点）共用公共动作 id，参数里用 domain 区分。
  • 校验：扩展 schema 独立文件 schema-ext-editing-0.1.json，主 schema 只校验 ext 为对象；未声明的域报错。

稳定 ID

  • PR：UXP 对象 guid（项目内持久）作为 native_id；达芬奇：TimelineItem.GetUniqueId()（待验证覆盖版本）；剪映草稿：segment id（UUID，明文版本可读）。
  • 统一 item_id = uuid5(session, app, native_id)；无 native_id 时，用 (media_id, source_in, record_in, track) 首见指纹 + 跨快照匹配（Hungarian，代价 = 源区间重叠 + 位置距离），标 id_basis: native|matched。
  • 切开后：左段保留原 ID，右段新 ID，并记录 split_from；合成/嵌套记录 parent_id。

时间线差分 changes[]

  • target = {type: item/track/marker/effect/timeline, id}，diff_level 沿用 exact/summary/changed_only，新增 paths 示例：record_in、source_out、speed.rate、effects[2].enabled。
  • 差分来源：native_event（PR DIRTY 等触发后读）/ poll（达芬奇）/ project_file（保存点解析 .prproj/草稿）。保存点差分只能到 changed_only 或 summary（中间步骤合并）。
  • 由 diff 推断 op：规则表（例：一个 item 消失 + 两个 item 出现且源区间连续、同 media → editing.clip.cut），标 provenance=derived、confidence。

预览行为

为什么要记

  • 剪辑师大量时间在看：找剪点（反复擦洗）、比较版本（来回播放）、检查节奏（整段播放）。这些是剪辑决策的直接前置信号。

记法：observation 事件，ext.editing.view

字段 含义 P
monitor source / program / timeline_scrub / fullscreen P0
mode play / scrub / jog / shuttle / step / loop / seek P0
from_frame / to_frame、obs_start_ns / obs_end_ns 区间 P0
rate 播放速率（含 JKL 倍速、倒放） P0
target media_id 或 timeline_id P0
visits[] 擦洗中停留点（停留 ≥ 300ms 的帧，最多 N 个） P1
reversals 方向反转次数（找点强度） P1
followed_by_ref 紧随其后的编辑步（派生） P0（derived）

采样/合并

  • 原始：PR 播放头位置轮询 100–200ms（UXP 读取播放头，具体 API 待验证）；达芬奇 GetCurrentTimecode 轮询 200ms；剪映只靠 L3 截帧 + JKL/空格键。
  • 合并：同一 monitor、同一 mode、间隔 < 500ms 的采样合成一个「播放段」；擦洗段保留方向反转点和停留点。落盘只存段，原始采样默认丢弃（调试模式保留）。
  • 预期量级：一小时剪辑 ≈ 数百到上千段，可接受。
  • 语义步：播放段不单独成步，作为下一编辑步的 event_refs(role=context)；连续 >N 秒纯观看可单独成 editing.review 步（P1）。

素材浏览与选择

  • editing.media.browse（观察）：打开 bin/文件夹、搜索词（哈希/授权后明文）、源监视器打开素材、源入出点设置（source_in/out 标记）。
  • 选中—打点—放入时间线串成「选材链」，是需求方最想要的「为什么选这个镜头」的证据。

意图与任务包

L4 意图（剪辑理由）

  • 形态：intent{origin, text, event_refs}，origin 取 human_verbatim（边剪边口述/事后看录屏口述）、human_annotated（事后文字）、model_augmented（模型补写，必须标 model）。
  • 剪辑理由分类标签（P1，intent.tags）：rhythm（节奏/卡点）、narrative（叙事顺序/信息揭示）、continuity（动作/视线衔接）、emotion、pacing（压缩/留白）、coverage（选镜头/选表演）、technical（跳帧、穿帮、音频问题修复）、client_note（甲方意见）。
  • 采集方式：P0 = 会话开头任务说明 + 结束后 15–30 分钟「看录屏口述」，挑关键剪点；P1 = 实时轻口述（热键开关麦克风）。

实现方案

结论

  • adb-mcp 只执行写操作，不录制。 链路是 MCP server（Python）→ 代理（Node socket.io，localhost:3001）→ UXP 插件（PR/PS/ID），AE 和 AI 走 CEP。两个仓库里都没有事件监听代码（没有 EventManager 或 app.bind）。
  • Contra 的「事件 payload 遥测」来自另一个未公开的录制器，adb-mcp 只用于「回放落地」。 依据：
    • parquet 234 步中有 211 个 tool_call，其中 64 个（约 30%）的名字（premiere_effect_param_change、premiere_clip_split、premiere_marker_change、premiere_keyframe_add 等）在 adb-mcp 里不存在；
    • 同一动作，录制名的参数和 fork 工具的参数也对不上：premiere_clip_split 用的是 insertion_time_ticks，fork 的 split_clip 用的是 tick；
    • fork 的 Premiere 提交信息写的是 "so recorded editing trajectories are fully replayable"，提交时间 2026-07-06，作者邮箱 @contra.com。 录制器具体怎么实现待验证；最可能是 UXP 面板订阅 EventManager，再读状态做差分，变化值以 from_value/to_value 形式写入。
  • 可复用： 两个仓库都是 MIT 许可（Copyright 2025 Mike Chambers），可以直接复用以下三块：
    • 状态读取： getSequences() 在每次命令返回时附带完整序列快照（轨道、片段、ticks），可以直接改成我们的快照器；
    • 回放： 33 个 PR 工具可当回放与校验器；
    • 工具名对齐： 用这套工具名做 execution_paths.mcp_tool，可以和 Contra 列对齐。 录制部分要自己写：在同一个 UXP 插件里加 EventManager 订阅和定时快照。
  • 其他软件： 达芬奇用 Studio 脚本轮询加差分（现成的 davinci-resolve-mcp，约 3.7k 星，MIT）；剪映/CapCut 用明文草稿差分加 L3（pyJianYingDraft 约 4.6k 星，Apache-2.0），不解密、不注入；FCP 用 FCPXML 保存点差分加 Workflow Extension（API 细节待验证）；AE 走 CEP/ExtendScript，adb-mcp 只给了一个 execute_extend_script。

结论（≤5）

  1. 三款开源都是「生成/改写草稿」工具，不是录制器。 没有进程内事件订阅；唯一现成差分是 capcut-cli 的只读 capcut diff A B（按 segment/material UUID 比 added/removed/changed）。采集必须自写：监视草稿目录 mtime → 读明文 JSON → 差分 → 推断 diff:* op。
  2. 加密只发生在剪映（app_source=lv），CapCut 国际版（cc）到 9.x 仍是明文。 剪映 5.9 是最后广泛使用的明文线；6.0+ 起 draft_content.json 常为 AES 二进制。例外（reported，单机）：剪映 9.0.0 Windows 应用自己创建的草稿是明文 draft_content.json（无 draft_info.json）；工具写入再打开时，draft_info.json 可保持明文，legacy 镜像被加密。11.4 macOS 读应用草稿受加密限制，写明文 draft_info.json 可被应用打开并就地升级为密文。
  3. 可解析字段（明文时）覆盖时间线主语义： tracks（video/audio/text/sticker/effect/filter）、segments（id、material_id、target/source_timerange µs、speed、volume、clip transform、common_keyframes、extra_material_refs）、materials（videos/audios/texts/stickers/effects/transitions/masks/animations…）、canvas/fps/duration、platform 版本标记。时间单位一律微秒；打开后时长会被量化到帧网格（CapCut 8.5 @30fps 已测）。
  4. 对象 ID 稳定： segment / track / material 都是 UUID；同一草稿内跨自动保存保持不变（capcut-cli diff/concat 以此为前提）。切开/新建产生新 UUID；无 native 事件时用 UUID 做 native_id，映射 item_id=uuid5(session,app,native_id)。
  5. 法律边界一致：检测加密、不解密。 pyJianYingDraft 拒合并解密 PR #189，改提供 fallback_loader 钩子且不内置实现；capcut-cli detectEncryption 只报告；VectCutAPI/pyCapCut 也只吃明文。第一阶段不跟 duo-video 等解密实现，不做 Qt hook / 进程注入。

流水线：

  1. L0：记录 app（jianying|capcut）、app_version、app_source、OS、草稿根路径、fps、快捷键配置导出（若有）。
  2. 草稿监视（L2 替代 = project_file 轮询）
  3. watchdog/ReadDirectoryChanges/FSEvents 盯 <draft_id>/ 下 canonical 文件（按 capcut-cli 选择规则：存在则优先 nested Timelines/<main>/…，否则 draft_info.json / draft_content.json）。
  4. 仅处理 detectEncryption 判定为明文者；密文 → 记 draft_encrypted=true，本会话降为 L3-only，保存点只存密文哈希与 mtime，不解析。
  5. 去抖 300–500ms；读全量 JSON；算 snapshot_hash；与上一快照做 UUID 对齐差分 → changes[]，provenance=project_file，diff_level 可达 exact（字段级）或保存稀疏时 summary。
  6. 推断 op_native=diff:… → op_canonical=editing.*（复用 03 词表）；confidence 低于 PR 事件路径。
  7. L3：截帧（编辑步前后 + 2s 低频）+ 键鼠坐标/快捷键；预览段靠空格/JKL/鼠标擦洗启发式合并（无播放头 API）。
  8. L1 AX：仅 ≤6.x Win 记菜单/导出对话框等；7+ / 11.x 记「不可用」即可，不依赖。
  9. 任务包：逐次复制明文草稿目录（或至少 canonical JSON + meta）进 project/；成片；media_manifest（哈希）；轨迹 jsonl；截帧；事后口述。密文会话的 project/ 只交加密 blob 哈希 + 导出成片，质量标 C−。

做不到什么（写清）

  • 无插件 API → 无 Contra 式 tool_call 遥测、无播放头精确采样、无选中项、无撤销栈事件。
  • 加密草稿 → 不解析时间线（本阶段）；中间剪辑步骤若未落盘明文则丢失，只靠 L3。
  • 自动保存间隔未官方保证 → 快速连点可能合并进一次 diff（多个逻辑 op 糊成一次 summary）。
  • 打开后 µs 量化 → 同一逻辑剪点帧号可能 ±1；对齐时用区间重叠而非精确相等。
  • 7+ AX 缺失 → 导出按钮/对话框名不可靠；导出完成靠输出文件出现 + L3。
  • 不回放进剪映（与 adb-mcp 回放 PR 不同）；VectCut/pyJianYingDraft 可作合成回放/校验（写新草稿），不能还原专家操作过程。
